## Medium (5)

### M1. 手写 SSE 取消后仍调用 `controller.close()`，在已关闭流上抛 TypeError

- **文件**: `app/api/ai/agent/route.ts:74-106`（7 处 `controller.close()`）、`app/api/ai/stream/route.ts:69`
- **维度**: 代码质量与潜在 Bug
- **描述**: 客户端 abort 触发流的 `cancel()` 回调后，流状态变为 closed；此时 `start()` 里检测到 `cancelled` 走的退出路径仍调用 `controller.close()`（agent 路由），或无条件的收尾 `controller.close()`（stream 路由 69 行，在 `!cancelled` 守卫之外）。已用 Node 实测：`cancel()` 后 `close()`/`enqueue()` 均抛 `TypeError: Invalid state: Controller is already closed`。异常被 streams 机制吸收（不 crash 进程），但这是「教学取消正确姿势」的代码自身在取消路径上抛错，部分运行时/版本中会以 unhandled rejection 进日志。
- **代码**:
  ```ts
  // stream/route.ts:66-69 — close() 在守卫之外
  if (!cancelled && !req.signal.aborted) {
      controller.enqueue(encoder.encode("data: [DONE]\n\n"));
  }
  controller.close(); // cancelled=true（流已 closed）时抛 TypeError
  ```
- **建议**: 加本地 `closed` 标志，或 `try { controller.close() } catch {}` 防护；`close()` 与 `[DONE]` 放入同一守卫内。agent 路由把各处 `{controller.close(); return;}` 收敛成一个幂等的 `finish()` 帮助函数。

### M2. sdk-chat 端点对请求体零防护：畸形 body 直接 500

- **文件**: `app/api/ai/sdk-chat/route.ts:98`（另见 :118-123）
- **维度**: 安全漏洞（用户输入未校验）
- **描述**: `await req.json()` 无 try/catch，body 非 JSON 时抛异常由框架兜底成 500（返回 HTML 错误页而非结构化 JSON）；`messages` 直接断言为 `UIMessage[]` 未做形状校验，`convertToModelMessages` 收到畸形消息同样抛错。这是全站唯一接受 POST body 的端点，也是唯一对外部输入完全不做防护的 Route Handler；本站 forms 专题专门教 zod 校验，此处与站内教学主张不一致。因是 mock model、无副作用，不定 High。
- **代码**:
  ```ts
  export async function POST(req: Request) {
      const { messages }: { messages: UIMessage[] } = await req.json();
      const result = streamText({
          model: mockModel,
          messages: await convertToModelMessages(messages),
      });
  ```
- **建议**: `try/catch` 包住 `req.json()` + `Array.isArray(messages)` 守卫，失败返回 400；或用已装的 zod 做 schema 校验，顺便成为「Route Handler 输入校验」正面示例；`convertToModelMessages` 抛错返回 422。

### M3. 外部 fetch 无超时：jsonplaceholder 挂起会无限挂住构建/ISR/接口

- **文件**: `data/blog.ts:77`
- **维度**: 性能问题
- **描述**: 文件头自己声明「jsonplaceholder 是全站唯一的构建期外部依赖」，catch 只兜住「出错」，兜不住「永不返回」——源站挂起（不响应也不断连）时 `next build`、ISR 再生与 `/api/blog` 请求都会挂到 undici 默认 300s headersTimeout 才落入兜底，fallback 机制迟迟不触发。（三个分区独立报到同一问题，已合并。）
- **代码**:
  ```ts
  const res = await fetch("https://jsonplaceholder.typicode.com/posts");
  if (!res.ok) {
    throw new Error(`jsonplaceholder responded ${res.status}`);
  }
  ```
- **建议**: `fetch(url, { signal: AbortSignal.timeout(10_000) })`（超时值提取为具名常量），让挂起也快速落入既有 fallback 分支。
